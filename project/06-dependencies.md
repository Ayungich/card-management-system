# 6. Функциональные и многозначные зависимости

## 6.1 Введение

Функциональные зависимости (ФЗ) и многозначные зависимости (МЗ) являются формальным представлением текстовых ограничений на данные. Они используются для проверки нормализации схемы БД.

**Обозначения:**
- `X → Y` — функциональная зависимость (X функционально определяет Y)
- `X →→ Y` — многозначная зависимость (X многозначно определяет Y)
- `X ↛ Y` — отсутствие функциональной зависимости

---

## 6.2 Функциональные зависимости (ФЗ)

### 6.2.1 Таблица USERS

**Атрибуты:** {id, username, email, password_hash, created_at, updated_at}

**Функциональные зависимости:**

1. **id → {username, email, password_hash, created_at, updated_at}**
   - Первичный ключ определяет все атрибуты
   - Источник: C-1 (Уникальность идентификаторов)

2. **username → id**
   - Username уникален, следовательно определяет пользователя
   - Источник: C-3 (Уникальность username)

3. **email → id**
   - Email уникален, следовательно определяет пользователя
   - Источник: C-4 (Уникальность email)

**Производные ФЗ:**
- `username → {email, password_hash, created_at, updated_at}` (транзитивность через id)
- `email → {username, password_hash, created_at, updated_at}` (транзитивность через id)

**Ключи-кандидаты:**
- `id` (первичный ключ)
- `username` (альтернативный ключ)
- `email` (альтернативный ключ)

**Вывод:** Таблица в BCNF (все детерминанты являются суперключами)

---

### 6.2.2 Таблица ROLES

**Атрибуты:** {id, name}

**Функциональные зависимости:**

1. **id → name**
   - Первичный ключ определяет название роли
   - Источник: C-1 (Уникальность идентификаторов)

2. **name → id**
   - Название роли уникально
   - Источник: C-8 (Предопределенные роли)

**Ключи-кандидаты:**
- `id` (первичный ключ)
- `name` (альтернативный ключ)

**Вывод:** Таблица в BCNF

---

### 6.2.3 Таблица USER_ROLES

**Атрибуты:** {user_id, role_id}

**Функциональные зависимости:**

1. **(user_id, role_id) → ∅**
   - Составной первичный ключ, нет неключевых атрибутов
   - Источник: C-10 (Уникальность пары)

**Ключи-кандидаты:**
- `(user_id, role_id)` (первичный ключ)

**Вывод:** Таблица в BCNF (нет неключевых атрибутов)

---

### 6.2.4 Таблица CARDS

**Атрибуты:** {id, card_number_encrypted, owner_id, balance, expiration_date, status, created_at, updated_at}

**Функциональные зависимости:**

1. **id → {card_number_encrypted, owner_id, balance, expiration_date, status, created_at, updated_at}**
   - Первичный ключ определяет все атрибуты
   - Источник: C-1 (Уникальность идентификаторов)

2. **card_number_encrypted → id**
   - Номер карты уникален, определяет карту
   - Источник: C-12 (Уникальность номера карты)

**Производные ФЗ:**
- `card_number_encrypted → {owner_id, balance, expiration_date, status, created_at, updated_at}` (через id)

**Отсутствующие ФЗ:**
- `owner_id ↛ id` — один пользователь может иметь несколько карт
- `balance ↛ id` — разные карты могут иметь одинаковый баланс
- `status ↛ id` — разные карты могут иметь одинаковый статус

**Ключи-кандидаты:**
- `id` (первичный ключ)
- `card_number_encrypted` (альтернативный ключ)

**Вывод:** Таблица в BCNF

---

### 6.2.5 Таблица TRANSACTIONS

**Атрибуты:** {id, from_card_id, to_card_id, amount, status, failure_reason, timestamp}

**Функциональные зависимости:**

1. **id → {from_card_id, to_card_id, amount, status, failure_reason, timestamp}**
   - Первичный ключ определяет все атрибуты
   - Источник: C-1 (Уникальность идентификаторов)

**Отсутствующие ФЗ:**
- `from_card_id ↛ id` — одна карта может участвовать в нескольких транзакциях
- `to_card_id ↛ id` — одна карта может участвовать в нескольких транзакциях
- `(from_card_id, to_card_id) ↛ id` — между двумя картами может быть несколько транзакций
- `timestamp ↛ id` — несколько транзакций могут произойти одновременно

**Ключи-кандидаты:**
- `id` (первичный ключ, единственный)

**Вывод:** Таблица в BCNF

---

### 6.2.6 Таблица AUDIT_LOGS

**Атрибуты:** {id, user_id, action, entity_type, entity_id, details, timestamp}

**Функциональные зависимости:**

1. **id → {user_id, action, entity_type, entity_id, details, timestamp}**
   - Первичный ключ определяет все атрибуты
   - Источник: C-1 (Уникальность идентификаторов)

**Отсутствующие ФЗ:**
- `user_id ↛ id` — один пользователь может создать несколько записей
- `entity_id ↛ id` — одна сущность может быть изменена несколько раз
- `timestamp ↛ id` — несколько действий могут произойти одновременно

**Ключи-кандидаты:**
- `id` (первичный ключ, единственный)

**Вывод:** Таблица в BCNF

---

## 6.3 Многозначные зависимости (МЗ)

### 6.3.1 Связь User → Role (через USER_ROLES)

**МЗ:** `user_id →→ role_id`

**Описание:** Пользователь может иметь несколько ролей независимо от других атрибутов

**Пример:**
```
user_id | role_id
--------|--------
u1      | USER
u1      | ADMIN
u2      | USER
```

Пользователь `u1` имеет обе роли, и эти роли независимы друг от друга.

**Источник:** C-9 (Каждый пользователь имеет хотя бы одну роль)

**Нормализация:** Многозначная зависимость устранена путем выделения в отдельную таблицу `user_roles`

---

### 6.3.2 Связь User → Card

**МЗ:** `owner_id →→ card_id` (в контексте таблицы CARDS)

**Описание:** Пользователь может иметь несколько карт независимо друг от друга

**Пример:**
```
owner_id | card_id | balance | status
---------|---------|---------|--------
u1       | c1      | 1000    | ACTIVE
u1       | c2      | 2000    | ACTIVE
u1       | c3      | 500     | BLOCKED
```

Пользователь `u1` имеет три карты, каждая со своими атрибутами.

**Источник:** C-11 (Каждая карта имеет ровно одного владельца)

**Нормализация:** Многозначная зависимость устранена путем выделения в отдельную таблицу `cards`

---

### 6.3.3 Связь Card → Transaction (as from_card)

**МЗ:** `from_card_id →→ transaction_id` (в контексте таблицы TRANSACTIONS)

**Описание:** Карта может быть отправителем в нескольких транзакциях независимо

**Пример:**
```
from_card_id | transaction_id | to_card_id | amount
-------------|----------------|------------|-------
c1           | t1             | c2         | 100
c1           | t2             | c3         | 200
c1           | t3             | c2         | 50
```

Карта `c1` участвует в трех транзакциях как отправитель.

**Источник:** C-18 (Каждая транзакция имеет карту-отправитель)

**Нормализация:** Многозначная зависимость устранена путем выделения в отдельную таблицу `transactions`

---

### 6.3.4 Связь Card → Transaction (as to_card)

**МЗ:** `to_card_id →→ transaction_id` (в контексте таблицы TRANSACTIONS)

**Описание:** Карта может быть получателем в нескольких транзакциях независимо

**Пример:**
```
to_card_id | transaction_id | from_card_id | amount
-----------|----------------|--------------|-------
c2         | t1             | c1           | 100
c2         | t2             | c3           | 150
c2         | t3             | c1           | 50
```

Карта `c2` участвует в трех транзакциях как получатель.

**Источник:** C-18 (Каждая транзакция имеет карту-получатель)

**Нормализация:** Многозначная зависимость устранена путем выделения в отдельную таблицу `transactions`

---

### 6.3.5 Связь User → AuditLog

**МЗ:** `user_id →→ audit_log_id` (в контексте таблицы AUDIT_LOGS)

**Описание:** Пользователь может создать несколько записей аудита независимо

**Пример:**
```
user_id | audit_log_id | action | entity_type | timestamp
--------|--------------|--------|-------------|----------
u1      | a1           | CREATE | Card        | 2025-01-01
u1      | a2           | BLOCK  | Card        | 2025-01-02
u1      | a3           | DELETE | Card        | 2025-01-03
```

Пользователь `u1` выполнил три действия, каждое записано независимо.

**Источник:** C-25 (Каждое изменение критичных данных логируется)

**Нормализация:** Многозначная зависимость устранена путем выделения в отдельную таблицу `audit_logs`

**Проверка:**

- ✅ transactions: все атрибуты атомарны

**Проверка:**

### 6.5.4 Нормальная форма Бойса-Кодда (BCNF)

**Требование:** Для каждой функциональной зависимости X → Y, X является суперключом

**Проверка:**

**users:**
- id → {username, email, ...} — id суперключ ✅
- username → id — username суперключ (альтернативный ключ) ✅
- email → id — email суперключ (альтернативный ключ) ✅

**roles:**
- id → name — id суперключ ✅
- name → id — name суперключ (альтернативный ключ) ✅

**user_roles:**
- (user_id, role_id) → ∅ — нет неключевых атрибутов ✅

**cards:**
- id → {...} — id суперключ ✅
- card_number_encrypted → id — card_number_encrypted суперключ (альтернативный ключ) ✅

**transactions:**
- id → {...} — id суперключ ✅

**audit_logs:**
- id → {...} — id суперключ ✅

**Вывод:** Все таблицы в BCNF

## 6.6 Граф зависимостей

```
USERS
  ├─ id → {username, email, password_hash, created_at, updated_at}
  ├─ username → id
  └─ email → id

ROLES
  ├─ id → name
  └─ name → id

USER_ROLES
  └─ (user_id, role_id) → ∅

CARDS
  ├─ id → {card_number_encrypted, owner_id, balance, expiration_date, status, created_at, updated_at}
  └─ card_number_encrypted → id

TRANSACTIONS
  └─ id → {from_card_id, to_card_id, amount, status, failure_reason, timestamp}

AUDIT_LOGS
  └─ id → {user_id, action, entity_type, entity_id, details, timestamp}
```
