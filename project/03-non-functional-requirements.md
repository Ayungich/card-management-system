# 3. Нефункциональные требования

## 3.1 Общие положения

Нефункциональные требования описывают **как** система должна работать: производительность, безопасность, надежность, масштабируемость и другие качественные характеристики.

---

## 3.2 Безопасность (Security)

### NFR-1: Шифрование номеров карт
**Описание:** Номера банковских карт должны храниться в зашифрованном виде

**Требования:**
- Алгоритм: AES-256
- Ключ шифрования хранится в переменных окружения (не в коде)
- Шифрование выполняется на уровне приложения перед сохранением в БД
- Расшифровка только при необходимости (для операций)

**Обоснование:** Защита от утечки данных при компрометации БД

**Реализация:** Класс `EncryptionUtil.java`

---

### NFR-2: Хеширование паролей
**Описание:** Пароли пользователей должны храниться в виде хешей

**Требования:**
- Алгоритм: BCrypt
- Стоимость (rounds): 10
- Соль генерируется автоматически для каждого пароля
- Невозможность обратного преобразования (хеш → пароль)

**Обоснование:** Защита от компрометации учетных записей

**Реализация:** Spring Security `PasswordEncoder`

---

### NFR-3: JWT-аутентификация
**Описание:** Система использует токен-базированную аутентификацию

**Требования:**
- Алгоритм подписи: HS256
- Access token:
  - Срок действия: 15 минут
  - Содержит: user_id, username, roles
- Refresh token:
  - Срок действия: 7 дней
  - Используется для обновления access token
- Секретный ключ:
  - Минимум 256 бит
  - Хранится в переменных окружения
  - Не передается клиенту

**Обоснование:** Stateless аутентификация, масштабируемость

**Реализация:** Класс `JwtUtil.java`, библиотека `jjwt`

---

### NFR-4: Маскирование номеров карт
**Описание:** При выводе номера карты клиенту показываются только последние 4 цифры

**Требования:**
- Формат: `**** **** **** 1234`
- Применяется во всех API ответах
- Полный номер доступен только внутри системы (для операций)

**Обоснование:** Защита от перехвата данных, соответствие PCI DSS

**Реализация:** Класс `CardMaskUtil.java`

---

### NFR-5: Ролевая модель доступа (RBAC)
**Описание:** Разграничение прав доступа на основе ролей

**Требования:**
- Роли: USER, ADMIN
- USER:
  - Доступ только к своим ресурсам
  - Запрет на просмотр чужих карт/транзакций
- ADMIN:
  - Полный доступ ко всем ресурсам
  - Управление пользователями и картами
- Проверка прав на уровне контроллеров (`@PreAuthorize`)

**Обоснование:** Защита данных, соответствие принципу наименьших привилегий

**Реализация:** Spring Security, аннотации `@PreAuthorize`, `@Secured`

---

### NFR-6: Защита от SQL-инъекций
**Описание:** Система должна быть защищена от SQL-инъекций

**Требования:**
- Использование параметризованных запросов (JPA/JPQL)
- Запрет на конкатенацию SQL из пользовательского ввода
- Валидация всех входных данных

**Обоснование:** Защита от атак на БД

**Реализация:** Spring Data JPA, Hibernate

---

### NFR-7: Защита от CSRF
**Описание:** Защита от межсайтовой подделки запросов

**Требования:**
- Для REST API CSRF отключен (используется JWT)
- Для web-интерфейса (если будет) — CSRF токены

**Обоснование:** Защита от атак CSRF

**Реализация:** Spring Security `csrf().disable()` для API

---

### NFR-8: CORS (Cross-Origin Resource Sharing)
**Описание:** Настройка политики CORS для фронтенда

**Требования:**
- Разрешенные origins: настраиваются через конфигурацию
- Разрешенные методы: GET, POST, PUT, PATCH, DELETE
- Разрешенные заголовки: Authorization, Content-Type
- Credentials: allowed

**Обоснование:** Интеграция с фронтендом, безопасность

**Реализация:** Класс `CorsConfig.java`

## 3.3 Производительность (Performance)

### NFR-9: Время отклика API
**Описание:** Система должна быстро обрабатывать запросы

**Требования:**
- Простые запросы (GET /api/cards): < 100ms
- Запросы с фильтрацией: < 200ms
- Переводы (POST /api/transfers): < 300ms
- Сложные отчеты: < 1000ms

**Измерение:** 95-й перцентиль при нагрузке 100 RPS

**Обоснование:** Удобство пользователей, конкурентоспособность

**Реализация:** Оптимизация запросов, индексы БД, кеширование

---

### NFR-10: Пагинация
**Описание:** Все списки должны поддерживать пагинацию

**Требования:**
- Размер страницы по умолчанию: 10 элементов
- Максимальный размер страницы: 100 элементов
- Параметры: `page` (номер страницы, начиная с 0), `size` (размер)
- Возврат метаданных: total_elements, total_pages, current_page

**Обоснование:** Снижение нагрузки на БД и сеть

**Реализация:** Spring Data `Pageable`, `Page<T>`

---

### NFR-11: Индексы БД
**Описание:** Часто используемые поля должны быть проиндексированы

**Требования:**
- Индексы на:
  - `cards.owner_id` (для поиска карт пользователя)
  - `cards.status` (для фильтрации по статусу)
  - `cards.card_number_encrypted` (уникальный индекс)
  - `transactions.from_card_id` (для истории)
  - `transactions.to_card_id` (для истории)
  - `transactions.timestamp` (для сортировки)
  - `audit_logs.user_id` (для аудита)
  - `audit_logs.entity_type, entity_id` (для поиска)

**Обоснование:** Ускорение запросов

**Реализация:** SQL DDL `CREATE INDEX`

---

### NFR-12: Connection Pooling
**Описание:** Использование пула соединений с БД

**Требования:**
- Пул: HikariCP (по умолчанию в Spring Boot)
- Минимальное количество соединений: 5
- Максимальное количество соединений: 20
- Timeout: 30 секунд

**Обоснование:** Эффективное использование ресурсов БД

**Реализация:** Конфигурация в `application.yml`

---

## 3.4 Надежность (Reliability)

### NFR-13: Транзакционность операций
**Описание:** Критичные операции должны быть транзакционными (ACID)

**Требования:**
- Переводы средств:
  - Атомарность: либо все операции выполнены, либо ни одна
  - Согласованность: баланс не может быть отрицательным
  - Изолированность: параллельные переводы не конфликтуют
  - Долговечность: изменения сохраняются после COMMIT
- Уровень изоляции: READ_COMMITTED (по умолчанию)
- Использование `FOR UPDATE` для блокировки строк

**Обоснование:** Целостность данных, защита от race conditions

**Реализация:** Spring `@Transactional`, PostgreSQL транзакции

---

### NFR-14: Обработка ошибок
**Описание:** Система должна корректно обрабатывать все ошибки

**Требования:**
- Единый формат ответа при ошибке:
  ```json
  {
    "timestamp": "2025-12-07T15:30:00Z",
    "status": 400,
    "error": "Bad Request",
    "code": "CARD_NOT_FOUND",
    "message": "Карта не найдена",
    "path": "/api/cards/123"
  }
  ```
- Коды ошибок:
  - 400: Ошибка валидации
  - 401: Не авторизован
  - 403: Доступ запрещен
  - 404: Ресурс не найден
  - 409: Конфликт (недостаточно средств, карта заблокирована)
  - 500: Внутренняя ошибка сервера
- Логирование всех ошибок

**Обоснование:** Удобство отладки, понятные сообщения для клиента

**Реализация:** `GlobalExceptionHandler`, кастомные исключения

---

### NFR-15: Логирование
**Описание:** Система должна логировать все важные события

**Требования:**
- Библиотека: SLF4J + Logback
- Уровни:
  - DEBUG: детальная информация (только в dev)
  - INFO: бизнес-события (создание карты, перевод)
  - WARN: подозрительные ситуации (неверный токен, истекшая карта)
  - ERROR: ошибки и исключения
- Файлы логов:
  - `logs/app.log` — все логи
  - `logs/error.log` — только ошибки
- Ротация:
  - `app.log`: 7 дней, максимум 100MB
  - `error.log`: 30 дней, максимум 50MB
- Формат:
  ```
  [2025-12-07 15:30:00.123] INFO [http-nio-8080-exec-3] c.a.cms.service.CardService - Card created: id=123
  ```
- Запреты:
  - Не логировать пароли
  - Не логировать полные номера карт
  - Не логировать JWT токены

**Обоснование:** Отладка, аудит, мониторинг

**Реализация:** `logback-spring.xml`

---

### NFR-16: Валидация входных данных
**Описание:** Все входные данные должны валидироваться

**Требования:**
- Использование Bean Validation (JSR-303)
- Аннотации:
  - `@NotNull`, `@NotBlank` — обязательные поля
  - `@Email` — валидация email
  - `@Size(min, max)` — длина строки
  - `@Min`, `@Max` — числовые диапазоны
  - `@Pattern` — регулярные выражения
  - `@Positive` — положительные числа
- Валидация на уровне DTO
- Понятные сообщения об ошибках

**Обоснование:** Защита от некорректных данных

**Реализация:** Spring Validation, аннотации в DTO

---

## 3.5 Масштабируемость (Scalability)

### NFR-17: Stateless backend
**Описание:** Приложение не должно хранить состояние между запросами

**Требования:**
- Аутентификация через JWT (не сессии)
- Нет in-memory хранилищ (или использовать Redis для кеша)
- Возможность запуска нескольких экземпляров приложения

**Обоснование:** Горизонтальное масштабирование

**Реализация:** JWT, stateless архитектура

---

### NFR-18: Контейнеризация
**Описание:** Приложение должно работать в Docker

**Требования:**
- Dockerfile для сборки образа
- Docker Compose для локальной разработки
- Образ должен быть оптимизирован (multi-stage build)
- Размер образа < 300MB

**Обоснование:** Упрощение развертывания, портативность

**Реализация:** `Dockerfile`, `docker-compose.yml`

---

### NFR-19: Конфигурация через переменные окружения
**Описание:** Все настройки должны выноситься в переменные окружения

**Требования:**
- Параметры БД: `DB_URL`, `DB_USER`, `DB_PASSWORD`
- JWT: `JWT_SECRET`
- Профиль: `SPRING_PROFILE` (dev/prod)
- Порт: `APP_PORT`
- Уровень логирования: `LOG_LEVEL`

**Обоснование:** Гибкость, безопасность (секреты не в коде)

**Реализация:** `.env` файл, Spring Boot externalized configuration

---

## 3.6 Сопровождаемость (Maintainability)

### NFR-20: Чистая архитектура
**Описание:** Код должен быть структурирован по слоям

**Требования:**
- Слои:
  - Controller (REST API)
  - Service (бизнес-логика)
  - Repository (доступ к БД)
  - Entity (модели данных)
  - DTO (передача данных)
  - Util (вспомогательные классы)
- Принципы:
  - Single Responsibility Principle
  - Dependency Inversion
  - Разделение concerns

**Обоснование:** Удобство поддержки, тестирования, расширения

**Реализация:** Layered Architecture

---

### NFR-21: Документация API
**Описание:** API должно быть документировано

**Требования:**
- Swagger/OpenAPI спецификация
- Swagger UI для интерактивного тестирования
- Описание всех эндпоинтов:
  - Параметры запроса
  - Формат тела запроса
  - Коды ответов
  - Примеры
- Доступ: `/swagger-ui.html`, `/api-docs`

**Обоснование:** Упрощение интеграции для фронтенда

**Реализация:** `springdoc-openapi`, аннотации `@Operation`, `@Tag`

---

### NFR-22: Покрытие тестами
**Описание:** Код должен быть покрыт тестами

**Требования:**
- Минимальное покрытие: 65% (по линиям)
- Типы тестов:
  - Unit-тесты (сервисы, утилиты)
  - Интеграционные тесты (контроллеры, репозитории)
- Фреймворки:
  - JUnit 5
  - Mockito (для моков)
  - Testcontainers (для интеграционных тестов с БД)
- Отчет о покрытии: JaCoCo

**Обоснование:** Качество кода, защита от регрессий

**Реализация:** Maven Surefire, JaCoCo plugin

---

### NFR-23: Миграции БД
**Описание:** Изменения схемы БД должны версионироваться

**Требования:**
- Инструмент: Liquibase
- Changelog файлы в формате YAML
- Версионирование: v1.0, v1.1, v2.0 и т.д.
- Откат (rollback) должен быть возможен

**Обоснование:** Контроль версий БД, упрощение развертывания

**Реализация:** Liquibase, `db/changelog/*.yaml`

---

## 3.7 Совместимость (Compatibility)

### NFR-24: Версия Java
**Описание:** Приложение должно работать на Java 21

**Требования:**
- Минимальная версия: Java 21 LTS
- Использование новых возможностей: Records, Pattern Matching, Virtual Threads (опционально)

**Обоснование:** Современные возможности языка, долгосрочная поддержка

---

### NFR-25: База данных
**Описание:** Приложение должно работать с PostgreSQL

**Требования:**
- Минимальная версия: PostgreSQL 14
- Рекомендуемая: PostgreSQL 16
- Совместимость с другими БД (MySQL, H2) не требуется

**Обоснование:** Надежность, производительность, поддержка JSON

---

### NFR-26: REST API
**Описание:** API должно соответствовать стандартам REST

**Требования:**
- HTTP методы:
  - GET — чтение
  - POST — создание
  - PUT/PATCH — обновление
  - DELETE — удаление
- Статус-коды:
  - 200 OK — успех
  - 201 Created — создано
  - 204 No Content — успех без тела ответа
  - 400 Bad Request — ошибка клиента
  - 401 Unauthorized — не авторизован
  - 403 Forbidden — доступ запрещен
  - 404 Not Found — не найдено
  - 500 Internal Server Error — ошибка сервера
- Content-Type: `application/json`
- Версионирование API: через URL (`/api/v1/...`) или заголовок

**Обоснование:** Стандартизация, совместимость

---

## 3.8 Доступность (Availability)

### NFR-27: Uptime
**Описание:** Система должна быть доступна большую часть времени

**Требования:**
- Целевой uptime: 99.5% (≈ 3.6 часа downtime в месяц)
- Плановое обслуживание: в ночное время
- Мониторинг доступности

**Обоснование:** Удобство пользователей

**Реализация:** Health checks, мониторинг

---

### NFR-28: Health checks
**Описание:** Система должна предоставлять информацию о своем состоянии

**Требования:**
- Эндпоинт: `/actuator/health`
- Проверки:
  - Доступность БД
  - Свободное место на диске
  - Использование памяти
- Формат ответа:
  ```json
  {
    "status": "UP",
    "components": {
      "db": {"status": "UP"},
      "diskSpace": {"status": "UP"}
    }
  }
  ```

**Обоснование:** Мониторинг, автоматическое восстановление

**Реализация:** Spring Boot Actuator
