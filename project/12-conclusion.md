# 12. Заключение и выводы

## 12.1 Резюме выполненной работы

В рамках курсовой работы была разработана полная схема реляционной базы данных для системы управления банковскими картами (Card Management System). Работа включала все этапы проектирования БД: от анализа требований до реализации на SQL.

### 12.1.1 Выполненные этапы

1. **Анализ предметной области и требований**
   - Определена целевая аудитория (клиенты банка и администраторы)
   - Описаны сценарии использования системы
   - Сформулированы 20 функциональных требований (FR-1...FR-20)
   - Определены 28 нефункциональных требований (NFR-1...NFR-28)

2. **Проектирование схемы БД**
   - Создана ER-диаграмма с 6 основными сущностями
   - Определены связи между таблицами (One-to-Many, Many-to-Many)
   - Описаны атрибуты каждой таблицы с типами данных и ограничениями

3. **Формализация ограничений**
   - Выведены 36 текстовых ограничений (C-1...C-36)
   - Ограничения охватывают целостность, уникальность, бизнес-логику, безопасность

4. **Анализ зависимостей**
   - Определены 10 функциональных зависимостей
   - Выявлены 5 многозначных зависимостей
   - Все зависимости формально описаны

5. **Нормализация**
   - Схема приведена к 4НФ (четвертая нормальная форма)
   - Устранены все аномалии обновления, удаления, вставки
   - Продемонстрирован пример проблем недонормализованной схемы

6. **Реализация на SQL**
   - Создан DDL скрипт (создание таблиц, индексов, триггеров, представлений, функций)
   - Разработаны 18 DML запросов для всех функциональных требований
   - Описаны 7 транзакций для критичных операций

## 12.2 Основные результаты

### 12.2.1 Схема базы данных

**Таблицы:**
- `users` — пользователи системы
- `roles` — справочник ролей (USER, ADMIN)
- `user_roles` — связь пользователей и ролей (Many-to-Many)
- `cards` — банковские карты
- `transactions` — история переводов
- `audit_logs` — системный аудит

**Характеристики:**
- Все таблицы в 4НФ
- Минимальная избыточность данных
- Полная ссылочная целостность через внешние ключи
- Каскадные операции для автоматического поддержания целостности

### 12.2.2 Функциональные возможности

**Для пользователей (USER):**
- ✅ Регистрация и авторизация
- ✅ Просмотр своих карт с фильтрацией
- ✅ Просмотр баланса и детальной информации
- ✅ Переводы между своими картами
- ✅ История транзакций

**Для администраторов (ADMIN):**
- ✅ Создание карт для пользователей
- ✅ Блокировка/активация карт
- ✅ Просмотр всех пользователей, карт, транзакций
- ✅ Логи аудита
- ✅ Статистика по системе

**Системные функции:**
- ✅ Автоматическая проверка истекших карт
- ✅ Валидация номера карты по алгоритму Луна
- ✅ Логирование всех критичных операций

### 12.2.3 Безопасность и надежность

**Безопасность:**
- Шифрование номеров карт (AES-256)
- Хеширование паролей (BCrypt)
- Маскирование номеров карт при выводе
- Ролевая модель доступа (RBAC)
- Защита от SQL-инъекций (параметризованные запросы)

**Надежность:**
- Транзакционность критичных операций (ACID)
- Блокировки для предотвращения race conditions (FOR UPDATE)
- Каскадные операции для поддержания целостности
- Append-only логи аудита (нельзя изменить или удалить)

**Производительность:**
- Индексы на часто используемые поля (13 индексов)
- Пагинация для всех списков
- Представления для упрощения сложных запросов
- Функции для повторяющихся операций

2. **Лимиты на переводы**
   - Таблица `transfer_limits` (дневной лимит, лимит на операцию)

   - Триггеры для автоматической отправки уведомлений

5. **Поддержка нескольких валют**
   - Таблица `currencies` (USD, EUR, RUB)
   - Поле `currency_id` в таблице `cards`

   - `mv_user_statistics` для быстрого доступа к статистике

3. **Кеширование**
   - Redis для кеширования часто запрашиваемых данных (баланс карты)
