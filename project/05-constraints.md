# 5. Текстовые ограничения на данные

## 5.1 Введение

Ограничения на данные выводятся из функциональных требований и обеспечивают целостность и корректность информации в базе данных. Каждое ограничение имеет уникальный идентификатор (C-N) для отслеживания.

---

## 5.2 Ограничения целостности сущностей

### C-1: Уникальность идентификаторов
**Описание:** Каждая запись в каждой таблице имеет уникальный идентификатор

**Формальное выражение:**
```
∀ table ∈ {users, roles, cards, transactions, audit_logs}:
  ∀ row1, row2 ∈ table: row1.id ≠ row2.id
```

**Реализация:** PRIMARY KEY на поле `id` в каждой таблице

**Источник:** Базовое требование реляционных БД

---

### C-2: Обязательность ключевых полей
**Описание:** Все первичные ключи и обязательные поля не могут быть NULL

**Формальное выражение:**
```
∀ table ∈ {users, roles, cards, transactions, audit_logs}:
  ∀ row ∈ table: row.id IS NOT NULL
```

**Реализация:** NOT NULL constraint на обязательные поля

**Источник:** Требования целостности данных

---

## 5.3 Ограничения на таблицу USERS

### C-3: Уникальность username
**Описание:** Имя пользователя должно быть уникальным в системе

**Формальное выражение:**
```
∀ user1, user2 ∈ users:
  user1.id ≠ user2.id ⇒ user1.username ≠ user2.username
```

**Реализация:** UNIQUE constraint на `users.username`

**Источник:** FR-1 (Регистрация)

**Обоснование:** Невозможность входа, если два пользователя имеют одинаковый username

---

### C-4: Уникальность email
**Описание:** Email должен быть уникальным в системе

**Формальное выражение:**
```
∀ user1, user2 ∈ users:
  user1.id ≠ user2.id ⇒ user1.email ≠ user2.email
```

**Реализация:** UNIQUE constraint на `users.email`

**Источник:** FR-1 (Регистрация)

**Обоснование:** Один email = один аккаунт (для восстановления пароля)

---

### C-5: Формат email
**Описание:** Email должен соответствовать стандартному формату

**Формальное выражение:**
```
∀ user ∈ users:
  user.email MATCHES regex '^[A-Za-z0-9._%+-]+@[A-Za-z0-9.-]+\.[A-Z|a-z]{2,}$'
```

**Реализация:** Валидация на уровне приложения (Bean Validation `@Email`)

**Источник:** FR-1 (Регистрация)

---

### C-6: Длина username
**Описание:** Username должен быть от 3 до 50 символов

**Формальное выражение:**
```
∀ user ∈ users:
  3 ≤ LENGTH(user.username) ≤ 50
```

**Реализация:** CHECK constraint или валидация на уровне приложения

**Источник:** FR-1 (Регистрация)

---

### C-7: Длина пароля
**Описание:** Пароль должен быть минимум 8 символов (до хеширования)

**Формальное выражение:**
```
∀ user ∈ users (при регистрации):
  LENGTH(password_plain) ≥ 8
```

**Реализация:** Валидация на уровне приложения (Bean Validation `@Size(min=8)`)

**Источник:** FR-1 (Регистрация), NFR-2 (Безопасность)

---

## 5.4 Ограничения на таблицу ROLES

### C-8: Предопределенные роли
**Описание:** В системе существуют только роли USER и ADMIN

**Формальное выражение:**
```
∀ role ∈ roles:
  role.name ∈ {'USER', 'ADMIN'}
```

**Реализация:** CHECK constraint или контроль на уровне приложения

**Источник:** FR-1, FR-9 (Роли пользователей)

---

## 5.5 Ограничения на таблицу USER_ROLES

### C-9: Каждый пользователь имеет хотя бы одну роль
**Описание:** Не может существовать пользователь без роли

**Формальное выражение:**
```
∀ user ∈ users:
  ∃ ur ∈ user_roles: ur.user_id = user.id
```

**Реализация:** Автоматическое назначение роли USER при регистрации

**Источник:** FR-1 (Регистрация)

---

### C-10: Уникальность пары (user_id, role_id)
**Описание:** Пользователю нельзя назначить одну и ту же роль дважды

**Формальное выражение:**
```
∀ ur1, ur2 ∈ user_roles:
  (ur1.user_id = ur2.user_id) ∧ (ur1.role_id = ur2.role_id) ⇒ ur1 = ur2
```

**Реализация:** PRIMARY KEY на `(user_id, role_id)`

**Источник:** Логика связи Many-to-Many

---

## 5.6 Ограничения на таблицу CARDS

### C-11: Каждая карта имеет ровно одного владельца
**Описание:** Поле owner_id не может быть NULL

**Формальное выражение:**
```
∀ card ∈ cards:
  card.owner_id IS NOT NULL ∧ ∃ user ∈ users: user.id = card.owner_id
```

**Реализация:** NOT NULL constraint + FOREIGN KEY на `cards.owner_id`

**Источник:** FR-3 (Просмотр своих карт)

---

### C-12: Уникальность номера карты
**Описание:** Номер карты (даже зашифрованный) должен быть уникальным

**Формальное выражение:**
```
∀ card1, card2 ∈ cards:
  card1.id ≠ card2.id ⇒ card1.card_number_encrypted ≠ card2.card_number_encrypted
```

**Реализация:** UNIQUE constraint на `cards.card_number_encrypted`

**Источник:** FR-9 (Создание карты)

**Обоснование:** Один номер карты = одна карта в системе

---

### C-13: Баланс не может быть отрицательным
**Описание:** Баланс карты всегда >= 0

**Формальное выражение:**
```
∀ card ∈ cards:
  card.balance ≥ 0
```

**Реализация:** CHECK constraint `CHECK (balance >= 0)`

**Источник:** FR-6 (Перевод средств)

**Обоснование:** Невозможность овердрафта

---

### C-14: Валидность статуса карты
**Описание:** Статус карты может быть только ACTIVE, BLOCKED или EXPIRED

**Формальное выражение:**
```
∀ card ∈ cards:
  card.status ∈ {'ACTIVE', 'BLOCKED', 'EXPIRED'}
```

**Реализация:** CHECK constraint `CHECK (status IN ('ACTIVE', 'BLOCKED', 'EXPIRED'))`

**Источник:** FR-11, FR-12 (Блокировка/Активация карты)

---

### C-15: Срок действия карты в будущем (при создании)
**Описание:** При создании карты срок действия не может быть в прошлом

**Формальное выражение:**
```
∀ card ∈ cards (при создании):
  card.expiration_date > CURRENT_DATE
```

**Реализация:** Валидация на уровне приложения (при создании)

**Источник:** FR-9 (Создание карты)

---

### C-16: Валидность номера карты по алгоритму Луна
**Описание:** Номер карты должен проходить проверку по алгоритму Луна

**Формальное выражение:**
```
∀ card ∈ cards:
  luhn_check(decrypt(card.card_number_encrypted)) = TRUE
```

**Реализация:** Валидация на уровне приложения (класс `CardNumberGenerator`)

**Источник:** FR-19 (Валидация номера карты)

**Обоснование:** Защита от ошибок ввода, стандарт индустрии

---

### C-17: Длина номера карты
**Описание:** Номер карты должен содержать ровно 16 цифр

**Формальное выражение:**
```
∀ card ∈ cards:
  LENGTH(decrypt(card.card_number_encrypted)) = 16
```

**Реализация:** Валидация на уровне приложения

**Источник:** FR-9 (Создание карты)

---

## 5.7 Ограничения на таблицу TRANSACTIONS

### C-18: Каждая транзакция имеет карту-отправитель и карту-получатель
**Описание:** Поля from_card_id и to_card_id не могут быть NULL

**Формальное выражение:**
```
∀ tx ∈ transactions:
  tx.from_card_id IS NOT NULL ∧ tx.to_card_id IS NOT NULL ∧
  ∃ card1 ∈ cards: card1.id = tx.from_card_id ∧
  ∃ card2 ∈ cards: card2.id = tx.to_card_id
```

**Реализация:** NOT NULL constraint + FOREIGN KEY

**Источник:** FR-6 (Перевод средств)

---

### C-19: Карта-отправитель и карта-получатель должны принадлежать одному пользователю (для USER)
**Описание:** Пользователь с ролью USER может переводить средства только между своими картами

**Формальное выражение:**
```
∀ tx ∈ transactions, user ∈ users (если user.role = 'USER'):
  ∃ card1, card2 ∈ cards:
    card1.id = tx.from_card_id ∧
    card2.id = tx.to_card_id ∧
    card1.owner_id = user.id ∧
    card2.owner_id = user.id
```

**Реализация:** Валидация на уровне приложения (сервис `TransferService`)

**Источник:** FR-6 (Перевод средств)

**Обоснование:** Безопасность, предотвращение несанкционированных переводов

---

### C-20: Сумма перевода должна быть положительной
**Описание:** Сумма перевода > 0

**Формальное выражение:**
```
∀ tx ∈ transactions:
  tx.amount > 0
```

**Реализация:** CHECK constraint `CHECK (amount > 0)`

**Источник:** FR-6 (Перевод средств)

---

### C-21: Достаточность средств на карте-отправителе
**Описание:** На карте-отправителе должно быть достаточно средств для перевода

**Формальное выражение:**
```
∀ tx ∈ transactions (при создании, если status = 'SUCCESS'):
  ∃ card ∈ cards:
    card.id = tx.from_card_id ∧
    card.balance ≥ tx.amount
```

**Реализация:** Валидация на уровне приложения (в транзакции)

**Источник:** FR-6 (Перевод средств)

**Обоснование:** Предотвращение отрицательного баланса

---

### C-22: Обе карты должны быть в статусе ACTIVE
**Описание:** Перевод возможен только между активными картами

**Формальное выражение:**
```
∀ tx ∈ transactions (при создании, если status = 'SUCCESS'):
  ∃ card1, card2 ∈ cards:
    card1.id = tx.from_card_id ∧
    card2.id = tx.to_card_id ∧
    card1.status = 'ACTIVE' ∧
    card2.status = 'ACTIVE'
```

**Реализация:** Валидация на уровне приложения

**Источник:** FR-6 (Перевод средств)

---

### C-23: Валидность статуса транзакции
**Описание:** Статус транзакции может быть только SUCCESS или FAILED

**Формальное выражение:**
```
∀ tx ∈ transactions:
  tx.status ∈ {'SUCCESS', 'FAILED'}
```

**Реализация:** CHECK constraint `CHECK (status IN ('SUCCESS', 'FAILED'))`

**Источник:** FR-6 (Перевод средств)

---

### C-24: Причина отказа указывается только для неудачных транзакций
**Описание:** Поле failure_reason заполняется только если status = FAILED

**Формальное выражение:**
```
∀ tx ∈ transactions:
  (tx.status = 'SUCCESS' ⇒ tx.failure_reason IS NULL) ∧
  (tx.status = 'FAILED' ⇒ tx.failure_reason IS NOT NULL)
```

**Реализация:** Валидация на уровне приложения

**Источник:** FR-6 (Перевод средств)

---

## 5.8 Ограничения на таблицу AUDIT_LOGS

### C-25: Каждое изменение критичных данных логируется
**Описание:** Операции создания, блокировки, активации, удаления карт и переводы должны записываться в audit_logs

**Формальное выражение:**
```
∀ operation ∈ {CREATE_CARD, BLOCK_CARD, ACTIVATE_CARD, DELETE_CARD, TRANSFER}:
  ∃ log ∈ audit_logs:
    log.action = operation ∧
    log.entity_id = affected_entity.id
```

**Реализация:** Автоматическое логирование в сервисах

**Источник:** FR-20 (Логирование критичных операций)

---

### C-26: Логи не могут быть удалены или изменены
**Описание:** Таблица audit_logs является append-only

**Формальное выражение:**
```
∀ log ∈ audit_logs:
  log не может быть изменен или удален после создания
```

**Реализация:** Ограничение прав доступа на уровне БД (только INSERT)

**Источник:** FR-16 (Логи аудита)

**Обоснование:** Целостность аудита, соответствие требованиям безопасности

---

### C-27: Валидность типа действия
**Описание:** Действие может быть только из предопределенного списка

**Формальное выражение:**
```
∀ log ∈ audit_logs:
  log.action ∈ {'CREATE', 'UPDATE', 'DELETE', 'BLOCK', 'ACTIVATE', 'TRANSFER'}
```

**Реализация:** CHECK constraint или контроль на уровне приложения

**Источник:** FR-16 (Логи аудита)

---

### C-28: Валидность типа сущности
**Описание:** Тип сущности может быть только из предопределенного списка

**Формальное выражение:**
```
∀ log ∈ audit_logs:
  log.entity_type ∈ {'Card', 'User', 'Transaction', 'Role'}
```

**Реализация:** CHECK constraint или контроль на уровне приложения

**Источник:** FR-16 (Логи аудита)

---

## 5.9 Ограничения на связи между таблицами

### C-29: Ссылочная целостность user_id в cards
**Описание:** Каждая карта должна ссылаться на существующего пользователя

**Формальное выражение:**
```
∀ card ∈ cards:
  ∃ user ∈ users: user.id = card.owner_id
```

**Реализация:** FOREIGN KEY constraint `cards.owner_id → users.id`

**Источник:** Базовое требование реляционных БД

---

### C-30: Ссылочная целостность user_id и role_id в user_roles
**Описание:** Каждая связь должна ссылаться на существующих пользователя и роль

**Формальное выражение:**
```
∀ ur ∈ user_roles:
  (∃ user ∈ users: user.id = ur.user_id) ∧
  (∃ role ∈ roles: role.id = ur.role_id)
```

**Реализация:** FOREIGN KEY constraints

**Источник:** Базовое требование реляционных БД

---

### C-31: Ссылочная целостность from_card_id и to_card_id в transactions
**Описание:** Каждая транзакция должна ссылаться на существующие карты

**Формальное выражение:**
```
∀ tx ∈ transactions:
  (∃ card1 ∈ cards: card1.id = tx.from_card_id) ∧
  (∃ card2 ∈ cards: card2.id = tx.to_card_id)
```

**Реализация:** FOREIGN KEY constraints

**Источник:** Базовое требование реляционных БД

---

### C-32: Ссылочная целостность user_id в audit_logs
**Описание:** Каждая запись аудита (если user_id не NULL) должна ссылаться на существующего пользователя

**Формальное выражение:**
```
∀ log ∈ audit_logs:
  (log.user_id IS NOT NULL) ⇒ (∃ user ∈ users: user.id = log.user_id)
```

**Реализация:** FOREIGN KEY constraint `audit_logs.user_id → users.id`

**Источник:** Базовое требование реляционных БД

---

## 5.10 Каскадные операции

### C-33: Удаление пользователя удаляет его карты
**Описание:** При удалении пользователя удаляются все его карты

**Формальное выражение:**
```
∀ user ∈ users (при удалении):
  ∀ card ∈ cards: card.owner_id = user.id ⇒ card удаляется
```

**Реализация:** FOREIGN KEY `cards.owner_id → users.id ON DELETE CASCADE`

**Источник:** FR-13 (Удаление карты)

---

### C-34: Удаление карты удаляет связанные транзакции
**Описание:** При удалении карты удаляются все транзакции, где она участвует

**Формальное выражение:**
```
∀ card ∈ cards (при удалении):
  ∀ tx ∈ transactions:
    (tx.from_card_id = card.id ∨ tx.to_card_id = card.id) ⇒ tx удаляется
```

**Реализация:** FOREIGN KEY `transactions.from_card_id → cards.id ON DELETE CASCADE`

**Источник:** Логика каскадного удаления

---

### C-35: Удаление пользователя обнуляет user_id в логах аудита
**Описание:** При удалении пользователя его user_id в логах становится NULL (логи не удаляются)

**Формальное выражение:**
```
∀ user ∈ users (при удалении):
  ∀ log ∈ audit_logs: log.user_id = user.id ⇒ log.user_id := NULL
```

**Реализация:** FOREIGN KEY `audit_logs.user_id → users.id ON DELETE SET NULL`

**Источник:** C-26 (Логи не могут быть удалены)

---

### C-36: Удаление роли удаляет связи в user_roles
**Описание:** При удалении роли удаляются все связи пользователей с этой ролью

**Формальное выражение:**
```
∀ role ∈ roles (при удалении):
  ∀ ur ∈ user_roles: ur.role_id = role.id ⇒ ur удаляется
```

**Реализация:** FOREIGN KEY `user_roles.role_id → roles.id ON DELETE CASCADE`

**Источник:** Логика каскадного удаления
