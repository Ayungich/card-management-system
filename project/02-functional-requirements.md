# 2. Функциональные требования

## 2.1 Общие положения

Функциональные требования описывают, **что** система должна делать. Каждое требование имеет уникальный идентификатор (FR-N) для отслеживания.

## 2.2 Требования для пользователя (роль USER)

### FR-1: Регистрация в системе
**Описание:** Новый пользователь может зарегистрироваться в системе

**Входные данные:**
- Username (уникальный, 3-50 символов)
- Email (уникальный, валидный формат)
- Password (минимум 8 символов)

**Выходные данные:**
- JWT access token (срок действия 15 минут)
- JWT refresh token (срок действия 7 дней)
- Информация о пользователе (id, username, email, roles)

**Бизнес-правила:**
- Username и email должны быть уникальными
- Пароль хешируется с использованием BCrypt
- Автоматически назначается роль USER
- Действие логируется в audit_logs

**API endpoint:** `POST /api/auth/register`

---

### FR-2: Авторизация в системе
**Описание:** Зарегистрированный пользователь может войти в систему

**Входные данные:**
- Username или email
- Password

**Выходные данные:**
- JWT access token
- JWT refresh token
- Информация о пользователе

**Бизнес-правила:**
- Проверка пароля через BCrypt
- При успешной авторизации генерируются новые токены
- При неудачной авторизации возвращается ошибка 401

**API endpoint:** `POST /api/auth/login`

---

### FR-3: Просмотр списка своих карт
**Описание:** Пользователь может просмотреть список всех своих карт

**Входные данные:**
- JWT токен (для идентификации пользователя)
- Параметры фильтрации (опционально):
  - status (ACTIVE, BLOCKED, EXPIRED)
  - Параметры пагинации (page, size)

**Выходные данные:**
- Список карт с информацией:
  - id
  - Маскированный номер карты (`**** **** **** 1234`)
  - Баланс
  - Срок действия
  - Статус
  - Дата создания

**Бизнес-правила:**
- Пользователь видит только свои карты
- Номер карты всегда маскируется (показываются только последние 4 цифры)
- Поддержка пагинации (по умолчанию 10 карт на страницу)
- Сортировка по дате создания (новые первыми)

**API endpoint:** `GET /api/cards`

---

### FR-4: Просмотр детальной информации по карте
**Описание:** Пользователь может просмотреть подробную информацию по конкретной карте

**Входные данные:**
- JWT токен
- ID карты

**Выходные данные:**
- Полная информация о карте (как в FR-3)

**Бизнес-правила:**
- Пользователь может просматривать только свои карты
- При попытке доступа к чужой карте возвращается ошибка 403

**API endpoint:** `GET /api/cards/{id}`

---

### FR-5: Просмотр баланса карты
**Описание:** Пользователь может узнать текущий баланс карты

**Входные данные:**
- JWT токен
- ID карты

**Выходные данные:**
- Баланс (с точностью до копеек)
- Валюта (RUB)
- Дата последнего обновления

**Бизнес-правила:**
- Пользователь может просматривать баланс только своих карт
- Баланс всегда >= 0

**API endpoint:** `GET /api/cards/{id}/balance`

---

### FR-6: Перевод средств между своими картами
**Описание:** Пользователь может перевести средства с одной своей карты на другую

**Входные данные:**
- JWT токен
- ID карты-отправителя
- ID карты-получателя
- Сумма перевода (положительное число)

**Выходные данные:**
- Информация о транзакции:
  - id
  - from_card_id
  - to_card_id
  - amount
  - status (SUCCESS или FAILED)
  - timestamp

**Бизнес-правила:**
- Обе карты должны принадлежать пользователю
- Обе карты должны быть в статусе ACTIVE
- На карте-отправителе должно быть достаточно средств
- Сумма перевода > 0
- Операция выполняется в транзакции (атомарно)
- При успехе:
  - Баланс отправителя уменьшается
  - Баланс получателя увеличивается
  - Создается запись в transactions (status=SUCCESS)
  - Создается запись в audit_logs
- При ошибке:
  - Баланс не изменяется
  - Создается запись в transactions (status=FAILED, указана причина)

**API endpoint:** `POST /api/transfers`

---

### FR-7: Просмотр истории транзакций
**Описание:** Пользователь может просмотреть историю своих транзакций

**Входные данные:**
- JWT токен
- Параметры фильтрации (опционально):
  - ID карты
  - Период (startDate, endDate)
  - Статус (SUCCESS, FAILED)
- Параметры пагинации (page, size)

**Выходные данные:**
- Список транзакций с информацией:
  - id
  - from_card_id (маскированный номер)
  - to_card_id (маскированный номер)
  - amount
  - status
  - failure_reason (если FAILED)
  - timestamp
  - direction (OUTGOING/INCOMING)

**Бизнес-правила:**
- Пользователь видит только транзакции по своим картам
- Сортировка по дате (новые первыми)
- Поддержка пагинации

**API endpoint:** `GET /api/cards/{id}/transactions`

---

### FR-8: Запрос на блокировку карты
**Описание:** Пользователь может отправить запрос на блокировку своей карты

**Входные данные:**
- JWT токен
- ID карты
- Причина блокировки (опционально)

**Выходные данные:**
- Подтверждение принятия запроса

**Бизнес-правила:**
- Пользователь может запросить блокировку только своей карты
- Фактическая блокировка выполняется администратором (FR-11)
- Запрос логируется в audit_logs

**API endpoint:** `POST /api/cards/{id}/block-request`

---

## 2.3 Требования для администратора (роль ADMIN)

### FR-9: Создание новой карты для пользователя
**Описание:** Администратор может создать новую карту для пользователя

**Входные данные:**
- JWT токен (роль ADMIN)
- ID владельца (пользователя)
- Начальный баланс (опционально, по умолчанию 0)
- Срок действия (по умолчанию +3 года)

**Выходные данные:**
- Информация о созданной карте

**Бизнес-правила:**
- Номер карты генерируется автоматически (16 цифр, проверка по Луну)
- Номер карты шифруется перед сохранением (AES-256)
- Статус по умолчанию: ACTIVE
- Действие логируется в audit_logs

**API endpoint:** `POST /api/admin/cards`

---

### FR-10: Просмотр всех пользователей
**Описание:** Администратор может просмотреть список всех пользователей

**Входные данные:**
- JWT токен (роль ADMIN)
- Параметры фильтрации (опционально):
  - Роль (USER, ADMIN)
  - Поиск по username/email
- Параметры пагинации

**Выходные данные:**
- Список пользователей с информацией:
  - id
  - username
  - email
  - roles
  - created_at
  - Количество карт

**Бизнес-правила:**
- Доступно только администраторам
- Пароли не возвращаются

**API endpoint:** `GET /api/admin/users`

---

### FR-11: Блокировка карты
**Описание:** Администратор может заблокировать карту

**Входные данные:**
- JWT токен (роль ADMIN)
- ID карты

**Выходные данные:**
- Подтверждение блокировки

**Бизнес-правила:**
- Статус карты изменяется на BLOCKED
- Операции с заблокированной картой невозможны
- Действие логируется в audit_logs

**API endpoint:** `PATCH /api/admin/cards/{id}/block`

---

### FR-12: Активация карты
**Описание:** Администратор может активировать заблокированную карту

**Входные данные:**
- JWT токен (роль ADMIN)
- ID карты

**Выходные данные:**
- Подтверждение активации

**Бизнес-правила:**
- Статус карты изменяется на ACTIVE
- Нельзя активировать карту с истекшим сроком действия
- Действие логируется в audit_logs

**API endpoint:** `PATCH /api/admin/cards/{id}/activate`

---

### FR-13: Удаление карты
**Описание:** Администратор может удалить карту из системы

**Входные данные:**
- JWT токен (роль ADMIN)
- ID карты

**Выходные данные:**
- Подтверждение удаления

**Бизнес-правила:**
- Карта удаляется физически из БД
- Связанные транзакции сохраняются (ON DELETE CASCADE не применяется к transactions)
- Действие логируется в audit_logs

**API endpoint:** `DELETE /api/admin/cards/{id}`

---

### FR-14: Просмотр всех карт
**Описание:** Администратор может просмотреть все карты в системе

**Входные данные:**
- JWT токен (роль ADMIN)
- Параметры фильтрации (опционально):
  - ID владельца
  - Статус (ACTIVE, BLOCKED, EXPIRED)
  - Период создания
- Параметры пагинации

**Выходные данные:**
- Список карт с информацией о владельцах

**Бизнес-правила:**
- Доступно только администраторам
- Номера карт маскируются
- Поддержка пагинации и сортировки

**API endpoint:** `GET /api/admin/cards`

---

### FR-15: Просмотр всех транзакций
**Описание:** Администратор может просмотреть все транзакции в системе

**Входные данные:**
- JWT токен (роль ADMIN)
- Параметры фильтрации (опционально):
  - Статус (SUCCESS, FAILED)
  - Период (startDate, endDate)
  - ID карты
- Параметры пагинации

**Выходные данные:**
- Список всех транзакций

**Бизнес-правила:**
- Доступно только администраторам
- Включая неудачные транзакции с причинами отказа

**API endpoint:** `GET /api/admin/transactions`

---

### FR-16: Просмотр логов аудита
**Описание:** Администратор может просмотреть логи всех действий в системе

**Входные данные:**
- JWT токен (роль ADMIN)
- Параметры фильтрации (опционально):
  - ID пользователя
  - Тип действия (CREATE, UPDATE, DELETE, BLOCK, ACTIVATE)
  - Тип сущности (Card, User, Transaction)
  - Период
- Параметры пагинации

**Выходные данные:**
- Список записей аудита:
  - id
  - user_id (кто выполнил)
  - action (что сделал)
  - entity_type (с какой сущностью)
  - entity_id (id сущности)
  - details (детали)
  - timestamp (когда)

**Бизнес-правила:**
- Доступно только администраторам
- Логи нельзя изменить или удалить
- Сортировка по дате (новые первыми)

**API endpoint:** `GET /api/admin/audit-logs`

---

### FR-17: Получение статистики по системе
**Описание:** Администратор может получить общую статистику

**Входные данные:**
- JWT токен (роль ADMIN)

**Выходные данные:**
- Статистика:
  - Общее количество пользователей
  - Общее количество карт
  - Количество активных карт
  - Количество заблокированных карт
  - Количество истекших карт
  - Общее количество транзакций
  - Количество успешных транзакций
  - Количество неудачных транзакций
  - Общий объем переводов (сумма)

**Бизнес-правила:**
- Доступно только администраторам
- Данные актуальны на момент запроса

**API endpoint:** `GET /api/admin/statistics`

---

## 2.4 Системные требования

### FR-18: Автоматическая проверка срока действия карты
**Описание:** Система автоматически проверяет срок действия карт

**Бизнес-правила:**
- При каждой операции с картой проверяется срок действия
- Если срок истек, статус автоматически меняется на EXPIRED
- Операции с истекшей картой невозможны
- Можно реализовать через scheduled task (раз в сутки)

---

### FR-19: Валидация номера карты по алгоритму Луна
**Описание:** Система проверяет корректность номера карты

**Бизнес-правила:**
- При генерации номера карты применяется алгоритм Луна
- При импорте карты извне проверяется по Луну
- Некорректные номера отклоняются

---

### FR-20: Логирование критичных операций
**Описание:** Система автоматически логирует все важные действия

**Бизнес-правила:**
- Логируются действия:
  - Создание/удаление пользователя
  - Создание/блокировка/активация/удаление карты
  - Переводы (успешные и неудачные)
  - Изменение ролей
- Логи сохраняются в audit_logs
- Логи нельзя удалить или изменить
