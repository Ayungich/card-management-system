# 8. Пример проблем из-за недонормализованности

## 8.1 Введение

В этом разделе рассматривается пример недонормализованной схемы БД для Card Management System и демонстрируются конкретные аномалии, которые возникают при работе с такой схемой.

---

## 8.2 Недонормализованная схема (2НФ, не 3НФ)

### 8.2.1 Описание схемы

Предположим, мы объединили таблицы `users` и `cards` в одну таблицу `user_cards`:

```sql
USER_CARDS (
    card_id UUID PRIMARY KEY,
    card_number_encrypted VARCHAR(255) UNIQUE NOT NULL,
    balance DECIMAL(15, 2) NOT NULL CHECK (balance >= 0),
    expiration_date DATE NOT NULL,
    status VARCHAR(20) NOT NULL,
    -- Данные пользователя (дублируются для каждой карты)
    user_id UUID NOT NULL,
    username VARCHAR(50) NOT NULL,
    email VARCHAR(100) NOT NULL,
    password_hash VARCHAR(255) NOT NULL,
    user_created_at TIMESTAMP NOT NULL,
    user_updated_at TIMESTAMP NOT NULL,
    -- Данные карты
    card_created_at TIMESTAMP NOT NULL,
    card_updated_at TIMESTAMP NOT NULL
)
```

### 8.2.2 Анализ нормальной формы

**Первичный ключ:** `card_id`

**Функциональные зависимости:**
1. `card_id → {card_number_encrypted, balance, expiration_date, status, user_id, username, email, password_hash, ...}`
2. `user_id → {username, email, password_hash, user_created_at, user_updated_at}`

**Проблема:** 
- ФЗ #2 показывает, что `username`, `email`, `password_hash` зависят от `user_id`, а не от `card_id` (первичного ключа)
- Это **транзитивная зависимость**: `card_id → user_id → username`
- Схема в **2НФ**, но **не в 3НФ**

**Проблема:** Данные пользователя `u1` (username, email, password_hash) дублируются 3 раза!

## 8.4 Аномалия обновления (Update Anomaly)

### 8.4.1 Сценарий

Пользователь john_doe решил изменить свой email с `john@example.com` на `john.doe@newmail.com`.

### 8.4.2 Необходимые действия

```sql
-- Нужно обновить ВСЕ строки с user_id = 'u1'
UPDATE user_cards
SET email = 'john.doe@newmail.com',
    user_updated_at = CURRENT_TIMESTAMP
WHERE user_id = 'u1';
```

### 8.4.3 Проблемы

1. **Неэффективность:**
   - Обновляются 3 строки вместо 1
   - Если у пользователя 100 карт, обновляются 100 строк
   - Увеличенная нагрузка на БД

2. **Риск несогласованности:**
   Если обновление прервется (сбой, ошибка транзакции), возможна ситуация:
   
   | card_id | user_id | email |
   |---------|---------|-------|
   | c1 | u1 | john.doe@newmail.com ✅ |
   | c2 | u1 | john.doe@newmail.com ✅ |
   | c3 | u1 | john@example.com ❌ |
   
   **Результат:** Один пользователь имеет два разных email в разных строках!

3. **Сложность запросов:**
   Чтобы получить актуальный email пользователя, нужно:
   ```sql
   -- Какой email правильный?
   SELECT DISTINCT email FROM user_cards WHERE user_id = 'u1';
   -- Может вернуть несколько значений!
   ```

### 8.4.4 Решение в нормализованной схеме

```sql
-- В нормализованной схеме (3НФ/4НФ):
-- Таблица USERS
UPDATE users
SET email = 'john.doe@newmail.com',
    updated_at = CURRENT_TIMESTAMP
WHERE id = 'u1';

-- Обновляется ОДНА строка
-- Все карты автоматически "видят" новый email через JOIN
```

## 8.5 Аномалия удаления (Delete Anomaly)

### 8.5.1 Сценарий

Пользователь john_doe решил удалить свою последнюю карту `c3` (предположим, c1 и c2 уже удалены).

### 8.5.2 Действие

```sql
DELETE FROM user_cards WHERE card_id = 'c3';
```

### 8.5.3 Проблема

**Результат:** Удаляется не только карта, но и ВСЯ информация о пользователе john_doe!

| card_id | user_id | username | email |
|---------|---------|----------|-------|
| c4 | u2 | jane_smith | jane@example.com |

Пользователь `u1` (john_doe) исчез из системы, хотя:
- Его аккаунт должен существовать
- Могут быть транзакции с его участием
- Могут быть записи в audit_logs

**Последствия:**
1. Невозможно восстановить информацию о пользователе
2. Нарушение ссылочной целостности (если есть транзакции с картами john_doe)
3. Потеря истории (логи аудита теряют связь с пользователем)

### 8.5.4 Решение в нормализованной схеме

```sql
-- В нормализованной схеме (3НФ/4НФ):
-- Таблица CARDS
DELETE FROM cards WHERE id = 'c3';

-- Удаляется ТОЛЬКО карта
-- Пользователь остается в таблице USERS
SELECT * FROM users WHERE id = 'u1';
-- Результат: john_doe все еще существует ✅
```

## 8.6 Аномалия вставки (Insert Anomaly)

### 8.6.1 Сценарий

Новый пользователь alice регистрируется в системе, но еще не получил ни одной карты.

### 8.6.2 Попытка вставки

```sql
-- Попытка создать пользователя без карты
INSERT INTO user_cards (user_id, username, email, password_hash, user_created_at, user_updated_at)
VALUES ('u3', 'alice', 'alice@example.com', '$2a$10$hash3', CURRENT_TIMESTAMP, CURRENT_TIMESTAMP);
```

### 8.6.3 Проблема

**Ошибка:** `card_id` является первичным ключом и не может быть NULL!

```
ERROR: null value in column "card_id" violates not-null constraint
```

**Варианты "решения" (все плохие):**

**Вариант 1: Создать "фиктивную" карту**
```sql
INSERT INTO user_cards VALUES
(
    'c_dummy_u3', 'DUMMY', 0.00, '2099-12-31', 'INACTIVE',
    'u3', 'alice', 'alice@example.com', '$2a$10$hash3', CURRENT_TIMESTAMP, CURRENT_TIMESTAMP,
    CURRENT_TIMESTAMP, CURRENT_TIMESTAMP
);
```
❌ Засоряет БД фиктивными данными

**Вариант 2: Использовать NULL для card_id**
```sql
-- Изменить схему: card_id может быть NULL
ALTER TABLE user_cards ALTER COLUMN card_id DROP NOT NULL;
```
❌ Теряется первичный ключ, нарушается целостность

**Вариант 3: Отложить регистрацию до создания карты**
❌ Нарушается бизнес-логика (пользователь должен существовать до карты)

### 8.6.4 Решение в нормализованной схеме

```sql
-- В нормализованной схеме (3НФ/4НФ):
-- 1. Создаем пользователя
INSERT INTO users (id, username, email, password_hash, created_at, updated_at)
VALUES ('u3', 'alice', 'alice@example.com', '$2a$10$hash3', CURRENT_TIMESTAMP, CURRENT_TIMESTAMP);

-- 2. Позже создаем карту (когда нужно)
INSERT INTO cards (id, card_number_encrypted, owner_id, balance, expiration_date, status, created_at, updated_at)
VALUES ('c5', '*encrypted_7890*', 'u3', 0.00, '2028-12-31', 'ACTIVE', CURRENT_TIMESTAMP, CURRENT_TIMESTAMP);

-- Пользователь и карта независимы ✅
```

## 8.7 Проблема избыточности данных

### 8.7.1 Расчет избыточности

**Предположения:**
- 10,000 пользователей
- В среднем 2 карты на пользователя = 20,000 карт

**Размер данных пользователя:**
- username: 50 байт
- email: 100 байт
- password_hash: 255 байт
- created_at: 8 байт
- updated_at: 8 байт
- **Итого:** ~420 байт на пользователя

**В недонормализованной схеме:**
- Данные пользователя хранятся в каждой строке карты
- 20,000 карт × 420 байт = **8.4 MB** данных пользователей

**В нормализованной схеме:**
- Данные пользователя хранятся один раз
- 10,000 пользователей × 420 байт = **4.2 MB** данных пользователей

**Избыточность:** 8.4 MB - 4.2 MB = **4.2 MB** (50% избыточности!)

### 8.7.2 Влияние на производительность

1. **Увеличенный размер таблицы:**
   - Больше страниц в памяти
   - Медленнее сканирование таблицы
   - Больше места на диске

2. **Медленнее операции обновления:**
   - Обновление email требует изменения N строк (где N — количество карт)
   - Увеличенная нагрузка на индексы

3. **Сложнее обеспечить целостность:**
   - Нужны триггеры для синхронизации данных
   - Риск несогласованности при параллельных обновлениях

## 8.8 Сравнение схем

| Критерий | Недонормализованная (2НФ) | Нормализованная (4НФ) |
|----------|---------------------------|----------------------|
| **Избыточность данных** | Высокая (50%) | Минимальная |
| **Аномалия обновления** | ❌ Есть (обновление N строк) | ✅ Нет (обновление 1 строки) |
| **Аномалия удаления** | ❌ Есть (потеря данных) | ✅ Нет (независимые сущности) |
| **Аномалия вставки** | ❌ Есть (нужна карта для пользователя) | ✅ Нет (независимые сущности) |
| **Целостность данных** | ❌ Риск несогласованности | ✅ Гарантируется FK |
| **Производительность UPDATE** | ❌ Медленно (N строк) | ✅ Быстро (1 строка) |
| **Производительность SELECT** | ⚠️ Быстрее (нет JOIN) | ⚠️ Медленнее (нужен JOIN) |
| **Размер БД** | ❌ Больше | ✅ Меньше |
| **Сложность запросов** | ✅ Проще (нет JOIN) | ⚠️ Сложнее (нужен JOIN) |
| **Масштабируемость** | ❌ Плохая | ✅ Хорошая |

## 8.9 Когда допустима денормализация?

Несмотря на проблемы, денормализация может быть оправдана в специфических случаях:

### 8.9.1 Read-heavy нагрузка

**Сценарий:** Система выполняет 99% SELECT и 1% UPDATE

**Пример:** Отчетная таблица для аналитики

```sql
-- Денормализованная таблица для отчетов (материализованное представление)
CREATE MATERIALIZED VIEW user_cards_report AS
SELECT 
    c.id AS card_id,
    c.card_number_encrypted,
    c.balance,
    c.status,
    u.id AS user_id,
    u.username,
    u.email
FROM cards c
JOIN users u ON c.owner_id = u.id;

-- Обновляется раз в сутки
REFRESH MATERIALIZED VIEW user_cards_report;
```

**Преимущества:**
- ✅ Быстрые SELECT (нет JOIN)
- ✅ Основные таблицы остаются нормализованными
- ✅ Контролируемая избыточность

---

### 8.9.2 Кеширование

**Сценарий:** Часто запрашиваемые данные кешируются

```sql
-- Основные таблицы нормализованы
-- Кеш в Redis/Memcached содержит денормализованные данные
{
  "card_id": "c1",
  "card_number": "*1234*",
  "balance": 1000,
  "user": {
    "username": "john_doe",
    "email": "john@example.com"
  }
}
```

**Преимущества:**
- ✅ Быстрый доступ
- ✅ БД остается нормализованной
- ✅ Кеш инвалидируется при обновлении

## 8.10 Выводы

1. **Недонормализованная схема (2НФ) приводит к серьезным проблемам:**
   - ❌ Аномалия обновления (несогласованность данных)
   - ❌ Аномалия удаления (потеря информации)
   - ❌ Аномалия вставки (невозможность создать пользователя без карты)
   - ❌ Избыточность данных (50% дублирования)
   - ❌ Сложность поддержки целостности

2. **Нормализованная схема (4НФ) устраняет все аномалии:**
   - ✅ Минимальная избыточность
   - ✅ Целостность данных
   - ✅ Независимость сущностей
   - ✅ Масштабируемость

3. **Денормализация допустима только:**
   - В специфических случаях (read-heavy, кеширование)
   - С контролируемой избыточностью
   - При сохранении нормализованной основной схемы

4. **Для Card Management System:**
   - Нормализация до 4НФ — правильное решение
   - Денормализация не требуется (сбалансированная нагрузка read/write)
   - Производительность SELECT достаточна с индексами и JOIN
